# Mémo 3D — DocGeo vs ancien DGPad

Notes techniques sur le système de coordonnées 3D de DocGeo et sur la
« fausse 3D » de l'ancien DGPad, pour préparer les futures conversions de
figures `.dgp` 3D. Écrit après l'import de [public/_Cube.dgp](public/_Cube.dgp)
(voir commit `ba77acb`).

## 1. DocGeo : la 3D est native, il n'y a pas de « mode »

Contrairement à l'ancien DGPad, DocGeo n'a **aucune distinction interne**
2D/3D :

- Tout point a des coordonnées `Vec3` ([point_object.ts](src/objects/point_object.ts)),
  la 2D n'étant qu'un cas particulier où `z = 0`.
- La projection écran est centralisée dans [projection.ts](src/projection.ts)
  (`projectPoint`) et pilotée par un `ProjectionFrame` porté par la grille
  ([grid_object.ts](src/objects/grid_object.ts)) : `ORG` (origine écran, `Vec2`),
  `UNIT` (`Vec3`), et deux angles de caméra `THETA`/`PHI`.
- Formule de projection (`projection.ts:19-29`) :
    ```
    sx = ORG.x + x*UNIT.x*sinPhi + y*UNIT.y*cosPhi
    sy = ORG.y + x*UNIT.x*cosPhi*sinTheta - y*UNIT.y*sinPhi*sinTheta - z*UNIT.z*cosTheta
    ```
- Caméra par défaut ([preferences.ts:154-158](src/preferences.ts#L154-L158)) :
  `theta = π/2`, `phi = 5π/2 ≡ π/2 (mod 2π)`. À ces valeurs, `cosTheta = 0` et
  la formule retombe exactement sur une projection orthographique 2D standard
  (`sx = ORG.x + x`, `sy = ORG.y − y`), **indépendante de z**. C'est pour ça
  qu'un fichier 2D classique s'importe déjà correctement sans aucun
  traitement spécial : ce n'est pas un « mode 2D », juste un angle de caméra
  particulier.
- Rotation interactive : clic-droit-glisser modifie `THETA`/`PHI` par
  `dx/dy * GRID.STEP` (`construction.ts:45-57`), avec `STEP = 0.015`
  ([preferences.ts:158](src/preferences.ts#L158)) — **cette constante est
  volontairement identique à `Math.coef3D` de l'ancien DGPad** (voir §2), donc
  déjà pensée pour la compatibilité de conversion.

**Conséquence pour toute conversion future** : ne jamais chercher à ajouter un
flag `is3D` ou un « mode » à `construction`/`GRID`. Toute figure legacy 2D ou
3D se traduit dans le même modèle unifié ; seule la _lecture_ de l'ancien
fichier a besoin de savoir si elle doit interpréter certains champs comme des
angles ou comme des positions écran (voir §3).

## 2. L'ancienne 3D de DGPad : une simulation, pas un vrai moteur

Code de référence : `/Volumes/SSD 2To/Google Drive/Sites/dgpad/scripts/`
(voir [AGENTS.md](AGENTS.md)).

- `Construction.js` porte un booléen `mode3D` (`is3D()`), indépendant du
  fichier — au niveau code il y a bien un fork `computeAll2D`/`computeAll3D`,
  contrairement à DocGeo.
- **Angles bruts recyclés** : en 3D, les variables `x0`/`y0` de
  `CoordsSystem.js` — qui _en 2D_ représentent l'origine écran — sont
  détournées pour porter les angles de rotation bruts. Conversion :
  `phi = x0 * Math.coef3D`, `theta = y0 * Math.coef3D`, avec
  `Math.coef3D = 0.015` en mode radian (`0.859436693` en mode degré) —
  voir `Interpreter.js:2082-2124, 2176-2184`.
- **Formule de projection** (`EX_point3D`, `Interpreter.js:2202-2210`) :
    ```
    sx = ox + x*sinPhi + y*cosPhi
    sy = oy - x*cosPhi*sinTheta + y*sinPhi*sinTheta + z*cosTheta
    ```
    Superficiellement l'inverse en `y` de la formule DocGeo — **mais
    vérifié empiriquement (voir §4) que la conversion directe
    `PHI = x0*0.015, THETA = y0*0.015` donne un rendu identique à l'ancien
    DGPad avec la formule DocGeo telle quelle**. Ne pas essayer de
    « corriger » un signe sans un cas de test réel qui le contredit.
- **Origine 3D implicite (`ORG3D`)** : dans une figure 3D, il n'y a pas de
  point `(0,0,0)` explicite. C'est **le premier point libre créé pendant que
  `mode3D` est actif** qui devient conventionnellement l'origine
  (`Construction.js:1000-1018`, `PointObject.js:349,600-606`). Les
  coordonnées `(x,y)` stockées pour ce point dans le fichier sont un résidu
  de sa position écran dans l'ancien éditeur — **sans signification
  mathématique**, à ignorer à l'import.
- **Points fixes 3D** (sommets de cube, etc.) : sérialisés
  `Point(nom, "[a,b,c]", "1")` — le 2ᵉ argument est le texte d'une
  expression (ici toujours un vecteur constant), le 3ᵉ est simplement
  `me.is3D() ? 1 : 0` écrit sous forme de chaîne (`PointObject.js:757-761`),
  **pas** une formule ou un flag de verrouillage. Ces points ne sont jamais
  draggables (`getSourceFixed`, pas `getSourceGeom`).
- Un point libre 2D « normal » reste sérialisé `Point(nom, x, y)` avec deux
  nombres, identique en 2D et en 3D — c'est la forme déjà supportée par
  DocGeo avant ce travail.

## 3. Ce qui a été porté côté import (`_Cube.dgp`)

Fichiers : [src/import/dgp_commands.ts](src/import/dgp_commands.ts),
[src/objects/fixed_point_object.ts](src/objects/fixed_point_object.ts).

- `SetCoords(x0,y0,unit,is3D,w,h)` : le 4ᵉ argument, jusque-là ignoré, est
  maintenant lu. Si `true`, `x0/y0` sont convertis en `GRID.PHI`/`GRID.THETA`
  (`raw * GRID.STEP`) au lieu de `GRID.ORG`. `is3D` est stocké dans
  `CommandContext` (import seulement, jamais dans `construction`/`GRID`).
- `Point` accepte deux formes : `(string, number, number)` (point libre,
  inchangé) et `(string, string, string)` (point fixe 3D) — dispatch selon
  le type de la 2ᵉ valeur résolue. La forme chaîne est parsée par
  `parseVectorLiteral` (littéral `[a,b,c]` uniquement, pas d'évaluateur
  d'expressions — cohérent avec la portée actuelle « lecteur », voir
  [AGENTS.md](AGENTS.md)) puis crée un `fixed_point_object` (pas de parents,
  `mousedrag` no-op, cf. `symmetry_object`/`midpoint_object`).
- Le premier point libre rencontré alors que `context.is3D` est vrai est
  épinglé à `[0,0,0]` (fixe, non draggable) au lieu de ses coordonnées
  littérales — décision produit confirmée avec l'utilisateur : **O ne doit
  pas rester déplaçable**, le panoramique de la scène 3D restera une
  opération caméra (`GRID.ORG`), pas un point de géométrie.

## 4. Vérification empirique faite

Calcul direct (`node -e`) de la projection des 8 sommets du cube avec
`PHI = 340*0.015`, `THETA = 12*0.015` (valeurs de `_Cube.dgp`) via la formule
DocGeo telle quelle : l'agencement relatif des 8 sommets autour de `O`
correspond à la capture d'écran de référence de l'ancien DGPad. Confirmé
ensuite visuellement par un screenshot Playwright du rendu réel
(`?url=/_Cube.dgp`) — correspondance quasi pixel-perfect. Pas de correction
de signe nécessaire.

## 5. Zones non couvertes / pièges pour la suite

- **Expressions non constantes** : un point fixe 3D dont le texte contient
  autre chose qu'un vecteur numérique littéral (référence à un autre point,
  opérateur, paramètre animé...) est rejeté avec une erreur explicite. Aucun
  évaluateur d'expressions n'existe côté DocGeo — à anticiper si de
  futures figures 3D en dépendent.
- **Plusieurs points libres dans une figure 3D legacy** : seul le premier
  devient l'origine ; les suivants, s'il y en a, garderaient leurs
  coordonnées littérales telles quelles (comportement de l'ancien moteur,
  jamais rencontré dans un fichier réel pour l'instant).
- **Flag `"0"`** (point fixe 2D, vecteur à 2 composantes) : géré par le
  parseur (`vector.length === 2` → `z = 0`) mais jamais vu ni testé sur un
  vrai fichier.
- **`SetCoordsStyle("3Dmode:true;...")`** : présent dans les fichiers 3D
  mais actuellement ignoré par l'import — l'information équivalente est déjà
  lue via le 4ᵉ argument de `SetCoords` (plus fiable car toujours en tête de
  fichier). À surveiller si un fichier venait à avoir `3Dmode` sans
  `SetCoords` cohérent.
- **Restrictions d'angle** (`EX_restrictPhi`/`EX_restrictTheta` côté ancien,
  `RESTRICT_THETA`/`RESTRICT_PHI` côté DocGeo) : pas encore reliées à
  l'import — DocGeo utilise ses propres bornes par défaut
  ([preferences.ts:156-157](src/preferences.ts#L156-L157)), pas celles
  éventuellement définies dans le fichier source.
